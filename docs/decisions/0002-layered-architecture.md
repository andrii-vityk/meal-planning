# 0002. Шарова архітектура з контролем залежностей

Статус: прийнято

## Контекст

Бізнес-логіка (список покупок, покриття, підбір) не повинна залежати ні від React, ні від платформи: її треба тестувати окремо й мати змогу змінити платформу без переписування.

## Рішення

Чотири шари в `src/`:

| Шар | Відповідальність | Може залежати від |
| --- | --- | --- |
| `domain` | сутності, чисті функції | — |
| `application` | сценарії використання, порти (інтерфейси сховища й AI) | `domain` |
| `infrastructure` | адаптери портів: платформа, in-memory | `application`, `domain` |
| `ui` | React-компоненти й хуки за фічами | `application`, `domain` |

`src/main.tsx` — точка композиції: єдине місце, що створює адаптери й передає їх в UI через React context (аналог DI-контейнера).

Порти лежать в `application`, бо їх визначають потреби сценаріїв, а не можливості платформи (інверсія залежностей).

Правила перевіряє ESLint (`no-restricted-imports` у `eslint.config.js`). Імпорти між теками — лише через аліас `@/`, відносні `../` заборонені, щоб правила не обходились відносними шляхами.

## Наслідки

- Локальна розробка й тести працюють на in-memory адаптерах, без платформи.
- Порушення меж ловить лінтер у CI, а не рев'ю.
- Для маленького застосунку шари легко перетворити на церемонію: абстракції додаються лише тоді, коли з'являється реальна потреба.
